# Experience-ranking weak-label experiment

## What is in this folder

- `ranking_candidates_labeled.csv` is the supplied OSM-derived candidate table.
- `estimation_parameters.json` contains the scenario and price/duration/ETA assumptions used to create estimates.
- `source_audit.json` records source counts and the original input hashes.

The CSV has 3,828 rows: 638 named OSM POIs crossed with exactly six analyst-created intent profiles. Those six profiles are the only query contexts; the file does not contain 3,828 real trip requests. Each POI is unique within each context. The benchmark holds whole POIs out between train, validation, and test so one POI cannot leak across splits.

## Provenance and limits

POI names, coordinates, OSM IDs, source links, OSM timestamps, opening-hour tags, and collection timestamps come from OpenStreetMap. An OSM record does not confirm that a place is currently open or still offers a given activity. Each candidate is a proposed POI visit, not a provider-confirmed activity or slot.

The labels are generated by `category_rule_weak_label`: grade 3 for the primary category, grade 2 for a related category, and grade 0 otherwise. There are no human preference labels (and no grade-1 rows). These labels are not a review of place quality or user satisfaction.

Every input row remains marked `training_eligible=false`. The benchmark accepts it only when the operator explicitly selects `--mode weak_label`; it does not change that source field or relabel the rows as verified.

The source explicitly marks the following estimates in `estimated_columns`: duration, ETA, price per person, relevance grade, and, where applicable, indoor status. The scenario uses an analyst-selected origin, walking-speed and route-factor assumptions, 180 minutes, two people, and a VND 600,000 group budget. Distances are Haversine distances, not road routes. The estimated duration and price are midpoints of analyst-selected category ranges, not current provider quotes. `is_hands_on` is blank because it was not observed.

`hard_feasible`, candidate slot IDs, planner evidence, and capacity verification are absent. `estimated_resource_feasible` is only the source's approximate time/budget screen. It is not a planner decision. In the application, the planner remains responsible for actual time, budget, capacity, locked stops, and route constraints; the ranker only scores candidates already accepted by that planner.

## Benchmark

Run the full comparison in Colab with `notebooks/LocalExplorerAI_Ranking_Benchmark_Colab.ipynb`, or locally from the repository root:

```powershell
python -m pip install -r apps/api/requirements-ranking-training.txt
python scripts/train_experience_ranker.py --mode weak_label
```

The script compares a tag/category rule baseline with LightGBM `LGBMRanker(objective="lambdarank")` and XGBoost `XGBRanker(objective="rank:ndcg")`. Both rankers receive the same API feature function, POI split, and four tuning configurations. Validation NDCG@5 selects the candidate; NDCG@10, latency, artifact size, and three-seed validation stability are supporting checks. Test metrics are calculated only for the selected model and baseline.

The default output is under `models/ai-ranker/weak-experiment/`. The directory is ignored by Git and is not the API's active bundle directory. An ML bundle is emitted only when it improves validation NDCG@5 over the rule baseline by at least 0.01. A weak-label bundle is always marked `deployment_eligible=false`; the API refuses to load it. If the rule baseline wins or ties, no ML bundle is created.

CatBoost is intentionally not included in this run: the shared feature contract is numeric, there are only six assumed query contexts, and the current labels are a deterministic category rule. An additional categorical learner would not add independent evidence of user preference and would increase tuning/overfit risk.

## Relation to the existing model

The repository's current artifact is an XGBoost ranker trained on `data/dataset_ranking_tphcm.csv`, an older, different, unverified dataset. Its stored NDCG@5 of 0.9516 on 34 held-out query groups is not comparable with this POI-held-out weak-label experiment. The ZIP's `model_checked/ranking_weak_label.joblib` is a `RandomForestRegressor` prototype, not a LambdaMART ranker. Its reported NDCG@10 of 1.0 measures agreement with the same weak category rule. The supplied joblib artifacts are not loaded or copied into the API.

The current ranker remains unchanged until consented user feedback or human-reviewed, provider-verified POI/activity/slot data supports a valid independent evaluation.

See [`docs/experience-ranker-benchmark.md`](../../../docs/experience-ranker-benchmark.md) for the initial local diagnostic results and the remaining LightGBM Colab run.
